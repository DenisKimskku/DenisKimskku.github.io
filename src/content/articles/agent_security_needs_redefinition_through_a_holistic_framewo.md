# Redefining LLM Agent Security: Why Content Filtering Fails 100% of AgentDojo and WASP Benchmark Tasks

As autonomous artificial intelligence (AI) agents transition from sandboxed playgrounds to production environments—executing code, managing databases, and calling financial APIs—security architectures remain dangerously hyper-focused on action content. Current defense paradigms evaluate threat levels by analyzing whether an instruction "looks" malicious, a strategy deployed in filters like PIGuard or evaluations like AgentDojo. However, this position paper from Vincent Siu et al. demonstrates that without authorization context, a security engine cannot differentiate between a legitimate administrative request and a high-severity breach.

## Background and Problem Setup

Existing evaluations treat agent security as a content classification problem. If an agent executes a command like "delete file," static benchmarks flag it as a failure. Conversely, if an agent blocks the command, it is marked safe. This binary framing conflates security with capability. An agent that refuses all potentially harmful actions is useless, while an agent that lacks the tool access to execute a malicious command is not "secured"—it simply lacks the capability to complete the task.

### Paradigm Comparison: Content-Based vs. Contextual Security

| Feature | Content-Based Paradigm (Current) | Contextual Security Paradigm (Proposed) |
| :--- | :--- | :--- |
| **Primary Metric** | Malicious-looking action strings (e.g., "delete user data", "send \$5000"). | Structural violations of authorization boundary properties. |
| **Unit of Analysis** | Isolated action text (snapshot evaluation). | Full execution trajectory and state history across sessions. |
| **Detection Focus** | Input filtering, pattern matching, adversarial text classifiers (e.g., PromptArmor). | Source tracking, goal specifications, data isolation, and provenance. |
| **Benchmark Design** | Single-turn task evaluations (e.g., AgentDojo, WASP). | Multi-session, continuous tracking of state degradation. |

As Section 2 highlights, treating security as content-based leads to miscategorized violations. For example, direct prompt injection and indirect prompt injection are often treated similarly, even though direct injection is a *Task Alignment* failure (the user requests an unauthorized objective) and indirect injection is a *Source Authorization* failure (the agent executes commands originating from an untrusted data source).

## Methodology

To operationalize contextual security, the authors decompose the security boundary into four jointly necessary properties that must be evaluated continuously across an agent's execution trajectory. 

```
                    ┌───────────────────────────┐
                    │      Incoming Action      │
                    └─────────────┬─────────────┘
                                  │
                     [ Source Authorization ] ──(Fail)──► [ BLOCK ]
                                  │ (Pass)
                       [ Task Alignment ] ────────(Fail)──► [ BLOCK ]
                                  │ (Pass)
                      [ Action Alignment ] ───────(Fail)──► [ BLOCK ]
                                  │ (Pass)
                       [ Data Isolation ] ────────(Fail)──► [ BLOCK ]
                                  │ (Pass)
                                  ▼
                             [ ALLOW ]
```

### The Four Properties of Contextual Security
1. **Source Authorization**: Asks *who* issued the command. A violation occurs when an agent acts on instructions originating from a source the deployer has not authorized to issue commands (such as text inside a processed email or a parsed webpage).
2. **Task Alignment**: Asks *what* the agent is trying to accomplish and if that overall objective is sanctioned. A violation occurs if the agent's governing objective diverges from the authorized task without explicit approval from an authenticated source.
3. **Action Alignment**: Asks *how* the agent is achieving the task. It evaluates whether each individual action serves the currently authorized objective. For example, running `rm -rf /production/database/` satisfies Task Alignment (resolving storage overflow) but violates Action Alignment (destroying the database is outside the authorized scope of that task).
4. **Data Isolation**: Governs whether information flows respect privilege boundaries across users, sessions, and tasks. A violation occurs when sensitive data from one context persists in memory and influences decisions in an unrelated context.

### Continuous Evaluation
A central theme of the paper is that security properties cannot be evaluated in static snapshots. Attacks like memory poisoning (Chen et al., 2024) write data at step $t_1$ that remains dormant until triggering an unauthorized action at step $t_n$. Snapshot benchmarks that reset context between turns are structurally incapable of detecting these temporal violations.

To prove the fundamental flaw of content-based defenses, the authors manually analyzed all 45 injection tasks across two major agent security benchmarks: AgentDojo (Debenedetti et al., 2024) and WASP (Evtimov et al., 2025). For every single task, they constructed a routine, legitimate scenario where an authenticated user would request the exact same action.

## Key Results

The manual analysis reveals that **100% of the evaluated injection tasks** across AgentDojo and WASP can be benign depending on context. This means any classifier trying to detect these attacks by looking at the action text alone faces a structural ceiling: it must choose between high false-positive rates (blocking legitimate workflows) or high false-negative rates (allowing attacks to pass).

By applying this framework to standard attack classes, we can reclassify familiar vulnerabilities into concrete, systemic authorization failures:

| Classical Attack Class | Content-Based Definition | Proposed Contextual Classification | Core Violated Property |
| :--- | :--- | :--- | :--- |
| **Indirect Prompt Injection** | System processes data containing embedded commands. | Confused deputy problem: agent uses its own authority to execute unauthorized commands. | **Source Authorization** |

## Limitations and Open Questions

While the paper's theoretical restructuring of agent security is robust, executing this framework in production presents several engineering challenges:

* **Overhead of Real-Time Alignment Checks**: Evaluating Task and Action Alignment continuously requires runtime checks (e.g., using secondary LLM-as-a-judge guardrails). This introduces latency and API cost penalties that may be unacceptable for real-time applications.
* **No Reference Implementation**: As a position paper, it does not provide an open-source, production-ready framework for tracking variable provenance or neural execution state.
* **Complex Intent Inference**: Distinguishing between "ordinary task refinement" (e.g., an agent updating a related security library while fixing an authentication bug) and true "Task Drift" is a highly subjective inference problem.

## What Practitioners Should Do

Relying purely on string-matching or prompt classifiers (like PIGuard) to inspect tool inputs is insufficient. Implement the following structural defenses:

### 1. Enforce Privilege Separation via Dual-LLM Architectures
To prevent Source Authorization failures, separate your system into a low-privilege processing engine and a high-privilege execution engine. 
- The low-privilege LLM processes untrusted data (e.g., reading emails or parsing webpages) and formats it strictly as structured data.
- The high-privilege LLM accepts only structured data from the low-privilege model and system commands from the authenticated user. It alone has access to execution tools.

### 2. Implement Strict Session and Memory Isolation
Enforce Data Isolation by treating agent memory like multi-tenant operating system memory.
- Clear short-term memory buffers completely between distinct sessions.
- If using Retrieval-Augmented Generation (RAG) or persistent memory, tag every retrieved chunk with cryptographic metadata indicating its source and owner.
- Implement permission-scoping checks on your vector database queries to ensure the agent cannot retrieve memory entries created in different user contexts.

### 3. Maintain Action Allowlists with Contextual Constraints
Instead of simple API-key limits, configure tool integration systems to validate Action Alignment dynamically:
- Ensure database write or file deletion tools check not just *if* they can run, but *which* task session ID spawned them.
- Block high-risk tool execution (e.g., file deletions or money transfers) if any part of the active context window contains tokens sourced from untrusted APIs or web scrapes.

## The Takeaway

Treating AI agent security as a content moderation challenge is a category error. By reframing agent security through the lens of classical systems authorization—Source Authorization, Task Alignment, Action Alignment, and Data Isolation—practitioners can build defenses that secure the execution path, regardless of how benign or malicious the surface text appears.

## Den's Take

While I agree that content-filtering is a dead end for agent security, this conceptual reframing stops short of addressing the massive operational headache of tracking context in production. Defining boundaries like Source Authorization and Data Isolation is easy on paper, but enforcing them across complex, multi-tool executions requires state-tracking engines that do not yet exist at scale. The authors’ mapping of 100% of AgentDojo and WASP tasks to benign workflows proves the diagnostic point, but it offers no concrete runtime architecture to implement these boundaries without triggering paralyzing latency.

As I've noted in previous reviews, relying on shallow safety layers often leads to unnecessary safety refusals because the guardrails lack structural awareness of the tool's execution flow. This paper's proposed taxonomy is a step forward, but we must stop trying to solve authorization at the model wrapper layer. True agent isolation will only succeed if we push these boundaries down to the OS and database level—treating the agent as an untrusted system process rather than trying to track its "intent" through LLM-driven provenance.
