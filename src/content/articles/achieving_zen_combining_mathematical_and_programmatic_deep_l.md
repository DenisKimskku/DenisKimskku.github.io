# Synthesizing Mathematical and Programmatic Representations for Black-Box Model Analysis

## TLDR
*   **What**: ZEN synthesizes model code and weights from memory.
*   **Who's at risk**: Forensic investigators analyzing proprietary DL systems.
*   **Key number**: ZEN was able to correctly attribute each to a base model even when the model had been customized by up to 83.3%.

## The Black-Box to White-Box Gap
Existing methods for converting black-box Deep Learning (DL) models to white-box models rely on recovering the mathematical representation—things like tensors, weights, and biases—using techniques such as operator loop analysis. These methods successfully identify basic layer types based on this recovered mathematical structure. Nevertheless, these techniques fundamentally ignore the DL model’s underlying code. This oversight renders model recovery, environment setup, and model re-execution impossible for any model incorporating customized code. Even when prior work attempts to export recovered artifacts into the universal ONNX format, this fails because ONNX strictly requires definitions for any customized or novel operator implementations to enable execution. Consequently, any model-testing technique that depends on instrumenting the model's code becomes inapplicable when the code is inaccessible.

## Unified Representation Synthesis
The central idea of ZEN is to move beyond merely recovering the mathematical representation ($\text{MR}$) and instead synthesize a unified representation that incorporates the model's programmatic representation ($\text{PR}$). This synthesis is achieved by treating the DL system as a composite entity, $\text{M} := (\text{MR}, \text{PR}, \phi, \text{E})$. The mapping function $\phi$ is what binds the mathematical elements ($\text{T}, \text{W}, \text{B}, \text{L}, \text{G}$) to their corresponding code elements ($\text{C}, \text{F}, \text{R}$). The key insight is that the programmatic representation for the DL model can be derived not from source code, but by investigating the code objects loaded into process memory during execution. By identifying and recovering code within the closure of the code implementing the DL model, ZEN captures the "how" of the model's operation alongside the "what."

## Code Object Filtering for Model Fingerprints
To build the unified representation, ZEN first recovers the mathematical representation using existing techniques. From this, it then recovers the entire DL system’s code objects from memory. The process involves enumerating all code objects, collecting their function signatures and class information, and recursively traversing pointers to verify all used functions and data structures are valid in memory. The mechanism then employs Code Object Filtering, utilizing the recovered model layer types and data structures to prune the vast set of recovered code objects. This filtering reduces the scope to only those code objects that specifically implement the DL model. This results in the model-specific programmatic representation, which is then synthesized with the mathematical representation to form the Unified Representation, serving as a robust fingerprint for attribution.

## Limitations
ZEN assumes a memory snapshot can be acquired without corruption, bypassing runtime encryption. The threat model is limited to Python-based DL systems, although extensions to C/C++ are discussed. The framework assumes the target DL system utilizes common DL frameworks (like PyTorch) and runs on a known OS/GPU hardware. Adversarial obfuscation techniques like layer renaming are insufficient to thwart ZEN because the system must still invoke standard underlying API operators.

## What practitioners should do
*   If you are forensic investigators, utilize memory acquisition tools against deployed DL systems to capture the runtime state for ZEN processing.
*   Leverage the Unified Representation generated by ZEN to compare against known base model fingerprints for accurate lineage attribution.
*   If custom modifications are detected between a recovered model and its attributed base model, use the generated patch file to re-implement the functionality on an open-source base model.
*   Apply white-box analysis tools to the patched, instrumentable model instance to test for adversarial vulnerabilities.

## Verdict
Read this paper if you work at the intersection of binary analysis, model forensics, and security auditing of proprietary AI deployments. Skip it if your work is confined to training or pure model design.

## Den's Take

The paper presents a functional path to linking runtime code to mathematical artifacts, which is a necessary step for robust model forensics. However, the reliance on acquiring a perfect memory snapshot—a prerequisite for the entire ZEN mechanism—introduces a practical fragility that the authors downplay. If an attacker can employ runtime obfuscation or memory masking techniques designed to disrupt standard process inspection before the snapshot is taken, the entire attribution chain breaks down. This vulnerability class is more immediate than the theoretical ability to reconstruct a model from memory. Furthermore, the system's success hinges on the model still invoking "standard underlying API operators" despite custom code; this suggests that any truly novel, low-level operator implementation will bypass the filtering mechanism entirely.
