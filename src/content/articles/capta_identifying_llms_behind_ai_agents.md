# CAPTA: Identifying LLMs Behind AI Agents via Preference Testing

## TLDR
*   **What**: Uses multiple-choice probes to infer backend LLM identity.
*   **Who's at risk**: Remote services interacting with LLM-based agents.
*   **Key number**: CAPTA achieves a mean identification accuracy of 99% with only 10 probes.

## Preference instead of capability
The current paradigm for LLM evaluation heavily relies on measuring model capabilities through tasks like math or code generation. This approach is insufficient for identifying the specific LLM powering an agent because different models can exhibit similar capabilities and yield the same correct answers. The setting CAPTA addresses involves a remote service that must identify the backend LLM of an agent interacting with it, often when the service only observes responses during task execution. Existing identification methods are limited because they either require direct querying of the LLM, rely on analyzing agent execution trajectories, or search for pre-embedded watermarks. CAPTA shifts the focus from what models *can* do (capability) to what models *prefer* to do when faced with the same input structure. This preference-based approach allows the remote service to gather identification signals solely through the agent's responses to verification challenges presented during normal service interaction.

## Diversity scoring and LLM-guided option-set optimization
The core innovation of CAPTA lies in its automated construction of discriminative probes, which tackles two intertwined challenges: selecting questions that differentiate models and optimizing the options for those questions. The insight is that questions where candidate LLMs generate diverse options are more likely to reveal underlying preference differences. To address the vast search space of possible questions, CAPTA employs a diversity scoring mechanism. This score, $D_q = 1 - \frac{1}{\sum_{o \in V_q} f(o)}$, ranks candidate questions based on the diversity of options generated by multiple LLMs. For the selected questions, CAPTA then uses an LLM as an optimizer to iteratively refine the option set, removing options until the set is maximally discriminative. This contrasts with prior methods that might require manual tuning or direct model access to test question effectiveness.

## Likelihood-based matching
The mechanism of CAPTA operates in two phases: preparation and runtime. In the preparation phase, after a question $q$ is selected, the LLM optimizer refines the option set $O$ to create an optimized probe $p = (q, O^*)$. CAPTA then constructs a reference fingerprint database ($\mathcal{F}$) by repeatedly querying a set of candidate models ($M$) with these optimized probes. For each model $m_k$ and probe $p$, a probability distribution is estimated from the observed responses. At runtime, the remote service presents the probes to the target agent and collects a sequence of responses $\mathbf{x} = \mathbf{x}_1, \ldots, \mathbf{x}_N$. Identification is achieved by matching this collected response sequence against the stored reference fingerprints ($\mathcal{F}$) using likelihood-based matching to infer the backend LLM $\hat{m}$.

## Limitations
The threat model is narrowly scoped to model identification; CAPTA does not address subsequent attacks like prompt injection against the identified model. Furthermore, the paper notes that CAPTA achieves 99.7% mean identification accuracy across all 28 agent–LLM combinations with 30 submitted answers.

## What practitioners should do
*   If deploying services that interact with LLM agents, consider implementing a preference-testing layer, analogous to CAPTA, to fingerprint backend models.
*   When developing LLM agents, be aware that the service provider can probe the agent's backend LLM's preferences, not just its task completion ability.
*   If building a model identification system, leverage diversity scoring to select questions that maximize inter-model choice variance.
*   For high-stakes interactions, plan for multi-interaction verification to improve identification accuracy against fluctuating model preferences.

## Verdict
Read this paper if you work on AI security, agentic workflows, or model provenance; otherwise, skip it as the mechanism is highly specific to the agent-service interaction model.

## Den's Take

The paper focuses heavily on *identification*—determining which model is running—but it glosses over the practical implications of what happens *after* identification. If a remote service successfully fingerprints an agent's backend LLM, the logical next step is to pivot from passive identification to active exploitation. The mechanism described, which relies on observing preference shifts during interaction, is entirely dependent on the service being able to repeatedly probe the agent. This reliance is a severe operational constraint; in any production system with rate limiting or session timeouts, the reported high accuracy is likely an overestimation of real-world utility. Furthermore, the paper correctly notes it avoids prompt injection, but it misses the obvious link: once a model is identified, an attacker has a known target profile, which significantly narrows the search space for tailored, high-impact attacks.
