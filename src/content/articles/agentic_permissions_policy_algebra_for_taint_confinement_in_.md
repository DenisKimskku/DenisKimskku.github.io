# Taming LLM Label Creep: Context Branching and Monoidal Policy Algebras in APPA

Connecting autonomous LLM agents to internal enterprise resources exposes them directly to prompt injection attacks, reasoning errors, and data exfiltration vectors. Traditional dynamic Information Flow Control (IFC) systems try to prevent these leaks by tracking security "taint" as data flows from sources to sinks. However, standard taint tracking suffers from a fatal usability flaw: once an agent reads a single highly restricted file, its entire execution context becomes permanently tainted—a phenomenon known as "label creep"—which immediately revokes its access to downstream tools and halts useful work. 

We present a detailed breakdown of Agentic Permissions Policy Algebra (APPA), a security framework designed to isolate unvetted data inside ephemeral child branches and verify security policies *before* data pollutes the primary trajectory context.

Furthermore, unlike structural partitioning frameworks like CaMeL [9] that require splitting the application into fixed multi-role orchestrations, APPA acts dynamically at the tool-dispatch layer, allowing standard single-agent loops to run securely.

## Technical Deep-Dive

APPA is mathematically formalized around a two-monoid algebraic model: one monoid governing security labels, and another governing a globally shared, append-only event log.

### The Label Monoid and Monotonic Descent

The label state is defined as:

$$S = \mathcal{P}(U) \times T$$

where $U$ is a finite set of principal (reader) identities (using decentralized reader sets) and $T$ is a finite trust chain. Because $S$ is a finite product lattice under component-wise meet ($\cap$, $\min$) and join ($\cup$, $\max$), policy composition rules are associative, commutative, and monotonic. 

A label is updated exclusively by folding action-contributed labels onto the existing state:

$$L' = L \wedge D$$

Because the update is a meet operation, trajectory labels descend monotonically under the partial order $\le$ and stabilize after a finite number of strict descents (Theorem 6.1). Crucially, this monotonicity ensures that security labels can only become more restrictive over time during a single trajectory.

### The Event Log Monoid and Committed Effects

To separate run-time history from value-granular confidentiality bounds, APPA models execution history as a free monoid over events under concatenation. Instead of querying raw history, policy preconditions evaluate a narrower projection of the log called the *committed-effect projection* $\mathcal{E}(\ell)$. 

Effects commit exactly once upon successful tool completion (`DispatchSucceeded` or `CloseSuccess`), filtering out failed or indeterminate execution attempts (as shown in Table 2):

$$\mathcal{E}(\ell \cdot e) = \begin{cases} \mathcal{E}(\ell) \uplus K & \text{if } e \in \{\text{DispatchSucceeded}(K), \text{CloseSuccess}(K)\} \\ \mathcal{E}(\ell) & \text{otherwise} \end{cases}$$

### Prospective Acquisition Enforcement

Rather than tracking taint reactively, the APPA engine interceptively simulates tool calls before dispatching them. The algorithm proceeds as follows:

```
Algorithm 1: Prospective Tool Check and Execution
Input: Current Trajectory Label L, Tool Call c, Global Log E
Output: Dispatch approval, Blocked state with Remedy Plan, or Refusal

1: Delta <- get_tool_delta(c)
2: L_prosp <- L \wedge Delta
3: 
4: // Check 1: Tool-Requirement Compatibility
5: if L_prosp < L then
6:     is_narrowing <- True
7: end if
8: 
9: if not satisfies_preconditions(c, L_prosp, E) then
10:    unmet_gaps <- get_unmet_preconditions(c, L_prosp, E)
11:    if is_narrowing then
12:        return BLOCKED(remedy_plan = Plan(Accept(L_prosp) + Authorize(unmet_gaps)))
13:    else
14:        return BLOCKED(remedy_plan = Plan(Authorize(unmet_gaps)))
15:    end if
16: end if
17: 
18: if is_narrowing then
19:    return BLOCKED(remedy_plan = Plan(Accept(L_prosp)))
20: end if
21: 
22: return DISPATCH_APPROVED
```

If a tool call restricts trajectory permissions ($L_{prosp} < L$), the engine triggers a *Narrowing Block*. This prevents the agent from executing the tool until it accepts the narrowing state. 

If there are also unmet requirements (e.g., missing approvals for a hard gate), the engine generates an atomic remedy plan containing `Accept` and `Authorize` steps. These are exposed to the agent as a static tool call `execute_remedy_plan(plan_id)`.

### Taint-Confining Branching Protocol

To read restricted or untrusted data without permanently narrowing the permissions of the primary parent trajectory, APPA orchestrates context branching (Figure 1):

1. **Initialization**: When a tool call would cause a narrowing block, the harness forks a child branch. The child inherits the parent's current label $L_c^0 := L_p^{init}$.
2. **Transcript Snapshot**: The child's context is seeded with the exact token prefix of the parent's model transcript up to the branch point. This is highly Key-Value (KV) cache-friendly, allowing inference engines to reuse cached states and avoid prompt re-synthesis overhead.
3. **Isolated Local Execution**: The agent performs the sensitive read and subsequent reasoning steps entirely within the child context. All updates apply locally to $L_c$, leaving the parent label $L_p$ completely unaffected.
4. **Checked Exit**: When child execution completes, it yields an exit signal. The return value $v$ is checked against the parent's security policy. If the returned value is sanitized or explicitly accepted, the parent merges the value:

$$L_p' = L_p \wedge \text{label}(v)$$

If the exit satisfies $L_p \le \text{label}(v)$, the parent's label is preserved exactly (Theorem 6.1), preventing permanent taint accumulation in the main loop.

### Critical Analysis of Results

An analysis of these metrics reveals several key insights:

1. **Drastic ASR Reduction**: Across all models, APPA consistently suppresses data exfiltration, dropping the baseline ASR of 31%–50% (under the `open` arms) to a mere 0%–7%.
2. **The Utility Recovery of Branching**: Comparing `APPA` (with branching) to `APPA-no-fork` (without branching) demonstrates the critical value of taint confinement. On GPT-5.6 Luna, branching recovers **26%** of lost absolute utility (rising from 69% to 95%). Similarly, utility jumps by **18%** on Qwen 3.6 35B and **16%** on Gemini 3.5 Flash-Lite.
3. **GPT-4o's Branching Penalty**: GPT-4o stands out as a clear exception to this pattern, showing flat utility (59%) both with and without branching. While GPT-4o successfully resolved 4 out of 9 branch-dependent tasks, these gains were completely offset by failures elsewhere driven by harness mediation overhead. This suggests that some model architectures struggle with the logical complexity of resolving multi-step remedy plans.
4. **Fides Security Gap**: Fides maintains an identical 29% ASR across all evaluated models in this benchmark. This represents a deterministic policy mismatch rather than model vulnerability; Fides relies on a rigid, ordinal confidentiality floor and cannot natively handle recipient sets, dynamic history predicates, or context branching.

## Limitations & Open Questions

While APPA is a robust framework, several technical limitations must be considered when evaluating its real-world security guarantees:

- **Lack of Side-Effect Rollback**: Context branching isolates the LLM's prompt transcript and context labels, but it does *not* provide transactional filesystem or database rollbacks. If an agent executes a tool inside a child branch that commits an external network egress or mutates a remote state, those physical side effects cannot be reverted if the child branch is discarded.
- **Dependency on Complete Tool Contracts**: APPA's prospective checks are only as reliable as the tool contracts provided. An undeclared write-side contract can allow data to bypass policies. For example, in the `joint-merger-brief` scenario, the agent successfully copied an HR value into the finance store because the `create_finance` tool did not declare a write-side restriction, enabling a "store-mediated laundering path."
- **Covert Channels**: APPA operates at the tool-interaction layer. It does not mitigate covert timing channels or adversarial content generation designed to leak information through subtle phrasing or metadata.

## What Practitioners Should Do

Security teams deploying multi-tool LLM agents should implement the following architectural changes based on APPA's design patterns:

### 1. Shift Policy Enforcement to Pre-Dispatch Hooks
Instead of relying on post-hoc LLM evaluation or sanitizing agent context after a tool returns, enforce checks *before* data acquisition. Use tool integration protocols—such as the Model Context Protocol (MCP)—to evaluate tool arguments and target contracts prior to execution.

### 2. Implement KV-Cache-Friendly Context Branching
When an agent needs to inspect unvetted or untrusted files (e.g., reading a user-uploaded PDF or parsing a public forum thread), spawn an ephemeral child branch. Because the child shares the exact token prefix of the parent trajectory, pre-branch states can be loaded directly from the KV cache without re-computing historical context tokens.

### 3. Move Authorization Logic to Single-Call Remedy Plans
Avoid scattered `if/else` logic across tool implementations. Consolidate policy violations into structured, machine-readable exceptions (such as `Accept` or `Authorize`). Present these as a unified "remedy plan" that the agent can execute via a single, atomic API call.

### 4. Separate Runtime Metrics from Context Taint Labels
Do not overload security taint labels with scalar tracking metrics like financial spend limits or call counters. Keep these constraints in a globally shared, append-only transaction log, and query them using state projections during prospective validation checks.

## The Takeaway

Dynamic taint tracking is mathematically sound but practically unusable when forced into standard linear agent architectures. APPA successfully demonstrates that dynamic information flow control can be made highly performant by shifting from a linear history to a branched context model. By isolating untrusted data inside disposable parent-seeded child trajectories, developers can enforce rigorous security policies without rendering their agents too restricted to perform useful work.

## Den's Take

I appreciate APPA's math-first approach to solving the "label creep" problem, but we need to talk about developer UX and hidden side channels. Standard dynamic taint tracking is notoriously rigid, so isolating untrusted tool outputs inside disposable, label-seeded child branches is an elegant engineering abstraction. However, this monoidal policy algebra assumes software developers can accurately model enterprise security policies as clean, associative algebraic folds over event logs. In practice, writing these mathematical formulations is incredibly error-prone, and a single mistake in the label join-semilattice could silently leak data. 

Moreover, while the paper claims to recover up to 26% of absolute utility, it glosses over the computational overhead and latency of running multiple speculative child branches. This structural complexity mirrors a pattern often seen in runtime safety layers, which frequently clash with the model's actual reasoning path, leading to unfaithful execution. If an agent operating inside an APPA child branch realizes it is in a sandboxed trajectory, it can still attempt to leak state through side-channels—such as timing attacks or structured resource exhaustion—before the branch is discarded. Practitioners should approach these algebraic promises with caution; the math is clean, but the deployment reality will be messy.
