# FedLSG: Mitigating Backdoor Poisoning in Federated Graph Neural Networks via LLM-Guided Semantic Calibration

As organizations increasingly deploy decentralized Graph Neural Networks (FedGNNs) for privacy-preserving distributed training in applications like recommender systems or social networks, they expose themselves to highly stealthy, poisoned model updates. Backdoor attacks like Distribution-Preserving Graph Backdoor Attack (DPGBA) or Unnoticeable Graph Backdoor Attack (UGBA) easily inject imperceptible trigger subgraphs into local training data, allowing malicious clients to compromise the aggregated global model. Because traditional, rule-based defenses fail to distinguish between stealthy trigger edges and benign non-IID (non-identically and independently distributed) structural variations, a new paradigm is required to safeguard collaborative graph learning systems.

### Threat Model

| | |
|---|---|
| **Attacker** | Compromised federated clients (up to 60% of the federation in the paper's experiments) with local data-poisoning capabilities. They can inject trigger subgraphs (e.g., SBA, UGBA, or DPGBA) into their private local training datasets. |
| **Victim** | Federated Graph Neural Networks (FedGNNs) undergoing iterative training across distributed clients. |
| **Goal** | Force the global aggregated model to classify target nodes containing the trigger subgraph into an attacker-chosen target class, while maintaining high classification accuracy on clean data. |
| **Budget** | Limited local poisoning budget (e.g., adding a small number of imperceptible trigger edges and nodes without triggering server-side volumetric anomaly detection). |

## Background / Problem Setup

Graph Neural Networks (GNNs) learn from rich topological structures, but their reliance on message passing makes them highly susceptible to backdoor triggers. In a federated setting (FedGNN), defending against this threat is exceptionally difficult because the central server cannot inspect the raw private graphs of the clients due to privacy constraints. 

Existing defenses fail at one of two levels:
1. **Local Pruning**: Methods like Prune [7] or Randomized Edge-Dropping (RIGBD [13]) rely on simple feature-similarity rules or random perturbations. While they work in centralized settings, applying them blindly across all clients in a federated system aggressively destroys benign graph structures, degrading clean model accuracy (ACC).
2. **Robust Aggregation**: Server-side defenses like Robust Learning Rate (RLR [15]) or energy-aware reweighting (FedTGE [16]) adjust client aggregation weights but lack any semantic understanding of the underlying graph patterns, leaving them blind to stealthy, distribution-preserving updates.

Furthermore, prior attempts to integrate LLMs into GNNs, such as LLM4FGL [17] or LG-DUMAP [18], require deploying full-scale LLMs directly on every local client. This is computationally prohibitive for edge devices.

### Defense Method Comparison

| Defense Method | Defense Level | Server-Side Privacy Leak? | Requires Local Full LLM? | Limitations |
|---|---|---|---|---|
| **Prune / PruneLD** [7] | Local edge pruning | No | No | Relies on simple topological rules; easily bypassed by stealthy triggers like DPGBA [8] that mimic clean feature distributions. |
| **RIGBD** [13] | Randomized edge-dropping | No | No | Randomly prunes edges, which degrades clean classification accuracy (ACC) and fails to eliminate targeted trigger structures. |
| **FedTGE** [16] | Aggregation-level weight adjustment | No | No | Lacks graph semantic understanding; struggles to distinguish between benign non-IID updates and malicious backdoor updates. |
| **LLM4FGL / LG-DUMAP** [17, 18] | Graph/Node level translation | No | Yes | High computational and communication overhead; deploying full-scale LLMs on resource-constrained client devices is impractical. |
| **FedLSG** (Proposed) | Hybrid (Local edge filtering + server aggregation) | No | No (Uses a lightweight LoRA-based student) | Introduces lightweight local student LLM inference overhead and requires template serialization. |

## Methodology

FedLSG addresses these challenges by partitioning semantic reasoning between a server-side **Teacher LLM** and client-side **Student LLMs** via Low-Rank Adaptation (LoRA) and parameter distillation. The defense functions across two distinct operational levels: edge-level filtering on the client, and update aggregation on the server.

```
                  [ Server-Side: Full Teacher LLM ]
                                  │
                       Distills Semantic Priors
                                  │
                                  ▼
[ Client 1: Student LLM ] ──► Computes Semantic Edge Scores ──► Filters Triggers
[ Client 2: Student LLM ] ──► Computes Semantic Edge Scores ──► Filters Triggers
                                  │
                     Uploads Model & LoRA Updates
                                  │
                                  ▼
                  [ Server-Side: Trust Aggregation ]
              (LLM scores client behavior vs. cohort baseline)
```

### 1. Client-Side LLM-Based Edge Modeling
To identify backdoor edges during message passing, each client runs a Similarity-Reweighted Graph Attention Network (SRGAT) backbone alongside a lightweight LoRA-based student LLM.

1. **Rule-Based Pre-Filtering**: The client calculates a topological anomaly score $r^{rule}_{uv}$ for each local edge $(u,v)$ based on homophily, cross-community connectivity, neighborhood overlap, and clustering consistency (as detailed in Section A.3, Eq. 37).
2. **Top-K Selection**: To minimize computational overhead, only the top-$K$ most suspicious edges (e.g., $K = 256$) are selected for deeper semantic inspection.
3. **Graph-to-Text Grounding**: The selected edges are serialized into natural language descriptions using a deterministic serializer. For instance:
   ```text
   "Edge (u, v): node u and node v share common neighbor; their community labels are different; local clustering around u is high while v shows weak connectivity..."
   ```
4. **LoRA Student Inference**: The lightweight student LLM processes these prompts alongside sampled neighbor contexts to compute a semantic suspiciousness score $r^{llm}_{uv}$ (Eq. 6).
5. **Score Fusion**: The structural and semantic risk scores are combined dynamically using adaptive fusion coefficients $a^{edge}_1$ and $a^{edge}_2$:
   $$\tilde{r}_{uv} = a^{edge}_1 r^{rule}_{uv} + a^{edge}_2 r^{llm}_{uv}$$
   $$\tilde{s}_{uv} = s_{uv}(1 - \kappa_e \tilde{r}_{uv})$$
   Here, $\tilde{s}_{uv}$ acts as the calibrated attention weight in the SRGAT backbone, dynamically down-weighting backdoor edges without removing them entirely.

### 2. Teacher-Student Knowledge Distillation
To keep the local student models lightweight, the central server maintains a full-scale LLM as a teacher and broadcasts global low-rank priors ($A^t, B^t$) to the clients. 
The client optimizes its GAT and student LLM parameters using a multi-level distillation loss (Eq. 13):
$$\mathcal{L} = \mathcal{L}_{CE} + \lambda_1 \mathcal{L}_{align} + \lambda_2 \mathcal{L}_{LoRA} + \lambda_3 \mathcal{L}_{distill}$$

Where:
- $\mathcal{L}_{CE}$ is the standard classification cross-entropy loss.
- $\mathcal{L}_{align}$ aligns local student weights with global teacher-derived low-rank parameters (Eq. 10).
- $\mathcal{L}_{distill}$ transfers node-level, graph-level, and edge-level structural and semantic knowledge from the server-side teacher to the client-side student (Eq. 12).

### 3. Server-Side Client Behavior Modeling
During the aggregation step, the server guards against malicious model updates by evaluating client updates relative to the cohort's baseline. 

1. **Behavioral Serialization**: The server converts client-level structural statistics (label entropy, parameter divergence, and student embeddings) into textual behavior summaries (Eq. 59).
2. **Cohort Evaluation**: The server constructs a global cohort prompt and uses the full LLM to evaluate the trustworthiness of each client $i$ relative to its peers, producing a semantic trust score $\tau^{llm}_{i,client}$.
3. **Trust-Aware Aggregation**: This score is combined with a rule-based behavioral trust score to calculate the final client aggregation weight $w^t_i$ (Eq. 16):
   $$w^t_i = 1 - \kappa_a(1 - \tilde{\tau}_{i,client})\omega_t$$
   Updates from anomalous or malicious clients are automatically downweighted, isolating the global model from poison.

### Critical Analysis of Results

While FedLSG consistently demonstrates superior defense performance over the baselines, a skeptical examination of Table 2 reveals certain limitations:
* **Residual Vulnerability on Large Graphs**: Under the distribution-preserving DPGBA attack on the large-scale `Ogb-arxiv` dataset, FedLSG's ASR is reduced to **30.21%**. While this is a massive improvement compared to the undefended model (95.35% ASR) and other baselines, a backdoor success rate of 30.21% still represents a successful exploit in nearly one-third of instances. In high-stakes environments, this residual vulnerability remains a threat.
* **The Complexity Trade-off**: The ablation study (Figure 4) shows that removing the client-side LLM (the "No LLM on Client" variant) causes the ASR to jump from **40.19% to 90.26%** under UGBA on Pubmed. This proves that local semantic inference is absolutely necessary for the defense, yet it introduces computational overhead on resource-constrained client devices.

## Limitations & Open Questions

### 1. Client-Side Inference Latency
Even though the local student LLM is pruned down to $k$ blocks (where $k=2$ semantic blocks), running local text-generation or scoring passes over $K = 256$ candidate edges in every training epoch introduces a compute bottleneck. On mobile edge devices or low-power IoT nodes, this process will severely impact battery life and training throughput.

### 2. Vulnerability to Template-Exploiting Adaptive Attackers
The conversion of graph structures to text relies on deterministic, rule-based serializers (Eq. 52). A sophisticated white-box attacker who knows the exact bucketization boundaries (Eq. 51) could mathematically optimize the injected trigger subgraphs to produce "benign-looking" textual profiles. This would allow the backdoor triggers to bypass the semantic filters of both the student and teacher models.

### 3. Parameter-Based Privacy Leakage
While the raw graph data remains local, clients upload their local LoRA parameters ($A_i, B_i$) and GAT parameters to the central server for trust evaluation and aggregation. Recent gradient-leakage attacks demonstrate that high-dimensional model updates can be exploited to reconstruct portions of local graph topologies, potentially compromising user privacy.

## What Practitioners Should Do

If you are deploying or securing federated graph neural networks, implement the following mitigations to protect your systems:

### 1. Right-Size the Local LLM Backbones
Do not deploy unnecessarily large models to edge clients. As Table 3 shows, the lightweight `Qwen2.5-0.5B-Instruct` achieves an ASR of **8.24%** under DPGBA on Pubmed—highly competitive with the much larger `Qwen-3-14B` (**7.25%** ASR). Deploying a sub-1B parameter student model drastically reduces local client compute costs with negligible impact on defense performance.

### 2. Implement Local Edge Pre-Filtering Budgets
To bound local client latency, enforce a hard cap on the number of edge candidates ($K$) evaluated by the local student LLM. Apply lightweight topological filtering on the client first:

```python
# Conceptual client-side candidate selection pipeline
def get_suspicious_edges(edge_index, node_features, budget_K=256):
    # 1. Compute fast structural anomaly scores (Eq. 37)
    rule_scores = compute_fast_structural_anomaly(edge_index, node_features)
    
    # 2. Extract top-K candidates to limit expensive LLM calls
    top_k_indices = argpart_sort(rule_scores, budget_K)
    return edge_index[:, top_k_indices]
```

### 3. Host the Teacher LLM with High-Throughput Frameworks on Secure Server Hardware
On the server side, deploy the full teacher model (e.g., `Gemma-3-12B-IT`) using high-throughput serving frameworks. Secure the server-side aggregation pipelines using Trusted Execution Environments (TEEs) to prevent malicious actors from observing the global cohort evaluation process.

### 4. Protect Low-Rank Updates with Secure Aggregation
To prevent the central server or a passive eavesdropper from reconstructing local graph topologies from the uploaded LoRA parameters ($A_i, B_i$), encrypt client-side parameters using Cryptographic Secure Multiparty Computation (SMPC) or add local Differential Privacy (DP) noise before transmission.

## The Takeaway

FedLSG proves that incorporating semantic-level context via LLMs can successfully defend federated GNNs against stealthy, distribution-preserving backdoor attacks that bypass traditional topological filters. By partitioning the workload between a server-side teacher and client-side LoRA students, the framework achieves high defense robustness without requiring full-scale LLM deployment on edge devices. However, because highly optimized attacks can still achieve up to a 30% success rate on massive datasets, semantic defense must be combined with strict compute constraints and privacy-preserving aggregation layers to survive in production.

## Den's Take

While reducing the attack success rate on `Ogb-arxiv` to 0.36% sounds like a clean sweep, I am highly skeptical of using natural language as an intermediary defense layer for structural graph data. Translating complex graph topologies into textual descriptions for LLM semantic reasoning introduces a glaring vulnerability: prompt injection. If an attacker knows the template used to serialize node attributes and edge connections into text, they can construct poisoned subgraphs whose natural language representations act as direct prompt injections—such as semantic payloads that instruct the evaluator LLM to override its training and classify the update as benign. 

Furthermore, the paper's evaluation overlooks the computational reality of decentralized networks. Even with a lighter "student" LLM on the client side, generating and processing these text descriptions adds massive execution overhead. In federated learning, local client hardware execution profiles can be highly vulnerable to side-channel analysis; introducing heavy, variable LLM processing workloads locally will only make client execution profiles more distinctive and easier to exploit. Until the authors test FedLSG against adaptive adversaries who target the LLM translation layer itself, this defense remains a fragile wrapper over a hard structural problem.
