# ToolHijacker: Automated Prompt Injection for LLM Agent Tool Selection Manipulation

## TLDR
* **What:** Novel optimization attack injecting malicious tool documents.
* **Who's at risk:** LLM agents using retrieval-based tool selection.
* **Key number:** ToolHijacker achieves high attack success rates in the no-box setting.

## What it is & who is affected
This paper introduces ToolHijacker, a new prompt injection attack designed specifically to manipulate the tool selection phase within Large Language Model (LLM) agents. These agents operate by retrieving relevant tools from a library and then having the LLM select the most appropriate one for a given task. ToolHijacker achieves this by automatically crafting a malicious tool document—comprising a name and a description—that is injected into the tool library. The attack functions in a "no-box" scenario, meaning the attacker cannot access the target system's internal components like the retriever or the LLM itself. This vulnerability affects any LLM agent deployment that relies on a two-step retrieval and selection mechanism for tool usage.

## Key findings
The effectiveness of ToolHijacker is demonstrated across multiple LLMs and retrievers in the constrained no-box setting. The attack is formulated as an optimization problem, solved via a two-phase strategy targeting retrieval and selection independently. When tested, ToolHijacker maintains substantial attack performance even when significant architectural mismatches exist between the shadow environment used for training and the target environment. For example, with Llama-3.3-70B as the shadow LLM and GPT-4o as the target LLM, our gradient-free method achieves a 96.7% attack success rate on MetaTool [22]. Additionally, ToolHijacker demonstrates high success during the retrieval phase, achieving a 100% attack hit rate on MetaTool. Furthermore, we show that ToolHijacker outperforms various prompt injection attacks when applied to our problem. Beyond the automated success, the paper evaluated several existing defenses. Both StruQ [23] and SecAlign [24] fail to defend against ToolHijacker, with our gradient-free attack achieving 99.6% success rate under StruQ. Among detection-based defenses, known-answer detection fails to identify malicious tool documents, while DataSentinel, PPL and PPL-W detect some malicious tool documents generated by the gradient-based method but miss the majority. For instance, PPL misses detecting 90% of malicious tool documents optimized via the gradient-based method, when falsely detecting < 1% of benign tool documents as malicious.

## Limitations
The threat model assumes the attacker can deploy a shadow pipeline, including a shadow retriever and shadow LLM, to guide the optimization process. This reliance on a shadow environment may not translate perfectly to real-world, black-box deployment where even the ability to run local simulations is restricted. Furthermore, the paper demonstrates failure against specific implementations, but this doesn't prove that treating all externally supplied tool documents as hostile inputs is sufficient; the downstream execution context of the selected tool remains an unaddressed attack surface.

## What practitioners should do
* Implement rigorous validation checks on tool descriptions before they are integrated into any production tool library used by an LLM agent.
* Recognize that existing detection defenses like PPL detection may fail to catch a large portion of sophisticated, gradient-based injection payloads.
* Prioritize defensive strategies that counter the end-to-end manipulation rather than focusing solely on individual retrieval or selection steps.
* When deploying agents, treat all externally supplied tool documents as hostile inputs, given the success of automated document crafting.

## Verdict
Read — especially if you are designing or securing LLM agents that rely on external tools. This work provides a concrete, automated methodology for a high-impact attack vector.

## Den's Take

The paper correctly identifies the high risk in retrieval-based agent tool selection, but its focus on automated document crafting misses the immediate, low-effort threat. While ToolHijacker requires an optimization pipeline, the practical vulnerability exists in the unsanitized ingestion pipeline. If an attacker can poison the tool library *once*—even through a less sophisticated, manual injection—the system is compromised, rendering the sophisticated gradient-free attack methodology a secondary concern for the immediate threat model. Furthermore, the evaluation against named defenses like StruQ and SecAlign is too narrow. The paper demonstrates failure against specific implementations, but this doesn't prove that treating all externally supplied tool documents as hostile inputs is sufficient; the downstream execution context of the selected tool remains an unaddressed attack surface.
