# MemSecBench: Tracking Agent Memory Poisoning from Persistence to Consequence and Repair

Persistent memory systems allow conversational agents to maintain user context and preferences across sessions, but they also open up a silent, highly persistent attack vector. When integrations like Mem0, A-MEM, or native file-based systems are embedded into enterprise workflows—such as document processing pipelines or customer support agents—attackers can inject malicious instructions that lie dormant. This paper introduces MemSecBench, a task-grounded benchmark designed to trace these poisoned memories from initial ingestion through downstream execution and eventual attempts at selective repair.

---

## Threat Model

The evaluation framework operates under a two-session threat model. In Session 1, an attacker injects a malicious payload. In Session 2, a benign user interacts with the agent, unwittingly triggering the exploit.

| Dimension | Details |
| :--- | :--- |
| **Attacker** | Black-box capability. Controls injected content through an input "Carrier" (such as a Workspace File, User Interaction, Supply-chain Tool, or External Content) but cannot directly edit backend state. |
| **Victim** | LLM agents using multi-session persistent memory (e.g., setups using OpenClaw or Hermes agent harnesses). |
| **Goal** | Force the agent to execute unauthorized actions, leak sensitive data, hijack execution flows, or cause goal drift during a subsequent benign session. |
| **Budget** | Negligible. Requires only a single poisoned entry in an ingested source (e.g., an onboarding PDF, a repository configuration file, or a chat transcript). |

## Background and Problem Setup

Prior research into agent security has largely evaluated memory issues in isolation. Some benchmarks focus entirely on whether an agent accepts a malicious write, while others test if an agent will execute a pre-seeded exploit. 

To formalize these differences, the authors compare MemSecBench against prior work across five dimensions of operational fidelity and benchmark completeness:
- **Intended Write (IW)**: Malicious content is written through the intended agent-facing memory interface.
- **Defined Consequence (DC)**: Memory activation leads to a verified, case-defined external outcome.
- **Successful Trigger Chain (ST)**: The same case-specific target semantics form a complete poisoning-retrieval-trigger chain.
- **Selective Recovery (SR)**: Evaluates the capability to remove malicious entries while preserving benign memories.
- **Multi-Backend Integration (MMI)**: Evaluates performance across diverse memory backends.

## Methodology

The benchmark consists of **310 linked task packages** across 48 realistic context scenarios spanning Code & Science, Daily Life, and Office Work. Each case is evaluated using a controlled **Write–Execute–Forget (WEF)** protocol in isolated Docker containers.

```
       [ Session 1: Write ]
                │
                ▼
   Is write API accepted? (W1)
                │
  Does semantic persist in DB? (W2)
                │
                ├──[ Session 2: Execute ]──────────┐
                │                                  │
                ▼                                  ▼
      Is memory recalled? (E1)          Is target removed? (F1)
                │                                  │
      Is memory adopted? (E2)           Are benign kept? (F2)
                │                                  │
                ▼                                  ▼
      External consequence? (E3)       Selective Repair? (SRSR)
```

The protocol proceeds through seven sequential checkpoint evaluations:

### 1. Write Stage
- **W1 (Write Operation)**: A deterministic programmatic check ensuring that the agent successfully invoked its memory write API during the initial transaction.
- **W2 (Persistence)**: An LLM-judged evaluation verifying if the added or modified backend database entries actually express the target malicious semantics.

### 2. Execute Stage
- **E1 (Recall Exposure)**: Tests if a subsequent, completely benign task query prompts the memory backend to retrieve the poisoned record.
- **E2 (Adoption)**: Tests if the recalled malicious instructions actively shape the agent’s reasoning, planning, or tool-use parameterization.
- **E3 (Externalization)**: Verifies if the agent executed the exploit against a controlled system service (e.g., sending an unauthorized email via Mailpit or writing an unapproved commit to a local GitLab instance).

### 3. Forget Stage
- **F1 (Repair)**: Evaluates if the agent, when prompted with a neutral security self-check, successfully deletes or neutralizes the target malicious entry.
- **F2 (Benign Preservation)**: Evaluates if the agent preserves all unrelated benign memories that were populated in the database before the attack.

The evaluations are adjudicated by a separate, pinned judge model (DeepSeek-V4-Pro) operating outside the execution runtime. To validate the judge's reliability, its verdicts were matched against human annotators, showing an accuracy of 90.60% and 91.80% respectively across a sample of 500 runs (Table 7).

### Notable Behavioral Observations

- **Adoption is the primary bottleneck**: As shown in the macro-averages in Figure 4, while write persistence remains high (84.2% at W2) and recall is common (76.1% at E1), there is a sharp drop-off when moving to adoption (dropping to 53.7% at E2). Once memory shapes reasoning, however, the exploit almost always succeeds (50.3% end-to-end success at E3).
- **Collateral damage hinders repair**: In the repair branch, 86.3% of poisoned agents succeeded in removing the malicious memory (F1). However, only 62.5% managed to preserve their benign memory entries (F2). This discrepancy drops the overall Selective Repair Success Rate (SRSR) to 56.1%.
- **No backend is universally secure**: Swapping a memory backend may mitigate one risk while compounding another. For example, under the OpenClaw / DeepSeek-V4-Pro setup, replacing a Native file-based memory store with A-MEM leaves the end-to-end attack success rate largely unchanged (dropping only slightly from 59.03% to 56.45%), yet it dramatically improves the selective repair success rate from 46.31% to 87.63%.

## Limitations & Open Questions

While MemSecBench presents a rigorous assessment framework, several technical design choices warrant scrutiny:

1. **Assumption of Successful Write Ingestion**: The benchmark assumes that the attacker-controlled text successfully reaches the memory store's write pipeline during Session 1. It does not evaluate the effectiveness of input-filtering firewalls or prompt shields that might intercept malicious instructions before they are committed to memory.
2. **Reliance on LLM-as-a-Judge**: Although the authors demonstrate a high agreement rate (~91%) with human annotators, the adjudication of the W2, E1, E2, F1, and F2 checkpoints depends on semantic evaluations performed by DeepSeek-V4-Pro. In production, highly sophisticated attacks might employ adversarial jailbreaks that confuse the evaluator model itself.
3. **Simulated State Restoration**: The transition from the Write stage to the Execute and Forget stages relies on restoring exact state snapshots of the memory databases. While appropriate for a controlled evaluation, this does not capture the natural drifting, fragmentation, or background indexing noise that occurs in continuously running production vector databases.

## What Practitioners Should Do

If you are deploying multi-session LLM agents utilizing persistent memory backends, consider implementing the following security controls:

### 1. Enforce Structured Metadata and Time-to-Live (TTL) Bounds
As illustrated by the "temporary onboarding instruction" scenario in Figure 1, memory backends often strip temporal context, turning a temporary guideline into a permanent operational rule. Configure your ingestion pipelines to append metadata fields, such as expiration timestamps and session provenance:

```python
# Conceptual memory storage schema incorporating strict temporal scoping
memory_entry = {
    "content": "Use temporary payment routing instructions valid only through June 30.",
    "metadata": {
        "created_at": "2026-05-30T10:00:00Z",
        "expires_at": "2026-06-30T23:59:59Z",
        "source_carrier": "workspace_file",
        "authority_level": "low"
    }
}
```

### 2. Isolate Read and Write Contexts
Do not allow agents to write directly to their global memory spaces when processing untrusted, third-party content (such as parsing external PDFs, incoming emails, or scraping web search results). Route memories generated from external documents into a low-trust, sandboxed scratchpad that requires human verification before being graduated to the primary agent profile memory.

### 3. Implement Strict Semantic Preservation Controls during Deletion
Because simple memory purges frequently destroy benign operational data (collateral deletion), build validation regression tests into your database maintenance routines. Before executing batch cleanups or user-requested deletion prompts, evaluate the delta of the memory state using a local semantic similarity check to ensure that safe, benign user preferences remain intact.

## The Takeaway

Securing LLM agents requires evaluating the entire lifecycle of persistent state rather than treating security as a simple, single-turn prompt-injection problem. MemSecBench highlights that while current LLM agents are highly susceptible to storing and executing poisoned memories, their greatest weakness lies in their inability to selectively clean up malicious entries without discarding critical benign context. Developers must move beyond native file writes and build structured, metadata-aware memory managers that treat state updates with the same rigor as database transactions.

## Den's Take

While evaluating the complete write-to-execute chain is a massive step forward from isolated security evaluations, I am highly skeptical of MemSecBench's focus on "selective recovery." Attempting to surgically purge poisoned semantic records from backends like Mem0 or A-MEM while keeping benign context intact is a fool's errand. Vector database state updates are not clean transactional operations; once an agent ingests malicious input, downstream decision boundaries are already skewed. 

As I noted when reviewing *Trojan Hippo* (Das et al. 2026), persistent memory functions as a silent, unmonitored exfiltration channel that bypasses session boundaries. MemSecBench confirms this danger with its 50.3% exploit chain success rate, but its clean, two-session threat model still oversimplifies reality. In live enterprise deployments, agents undergo complex, asynchronous memory updates across dozens of concurrent user tasks, making sequential, clean "repair" practically impossible. 

Instead of trying to patch memory post-facto, developers must treat persistent stores as untrusted, high-risk inputs. Security teams should focus on enforcing runtime access controls on what a recalled memory is allowed to trigger, rather than hoping they can sanitize the vector store itself.
