## TLDR
- **What**: SPORE (State Persistence-based Memory Extraction) is an extraction attack that bypasses LLM agent memory isolation by decoupling adversarial control commands (stored in short-term memory) from pure semantic retrieval anchors, systematically exfiltrating private long-term memory via outgoing tool-call parameters.
- **Who's at risk**: Multi-user LLM agent systems and orchestration frameworks (e.g., Dify, Coze, LangChain, Mem0) that automatically retrieve long-term user memories into context and integrate third-party APIs or external tools.
- **Key number**: SPORE achieves an 80.0% Record Extraction Rate (RER) on GPT-5-mini in trigger-unlimited settings, and maintains up to a 67.5% extraction rate on commercial platforms like Coze using only 20 triggers.

# Exposing the Tool-Side Leakage Vector: Explaining the SPORE Persistence-Based Memory Extraction Attack on Isolated LLM Agents

Production-grade Large Language Model (LLM) agents deployed across platforms like OpenAI, Anthropic, and Mem0 rely heavily on user-level memory isolation to secure private user data stored in Long-Term Memory (LTM). This architectural boundary binds each user's LTM to a unique identifier, preventing cross-user data exposure and neutralizing traditional shared-storage extraction attacks. 

However, this design assumes that memory isolation on the user-side is sufficient to guarantee data privacy. SPORE breaks this assumption by exposing the tool-side boundary: when an agent executes external APIs, it routinely includes retrieved LTM data in its outgoing invocation parameters. This architectural pattern establishes an unmonitored exfiltration channel directly to malicious third-party tools, bypassing traditional user-level isolation safeguards.

## Technical Deep-Dive

### The Retrieval-Interference Bottleneck
Traditional attacks adapt to the tool-side by returning a combined payload containing both a retrieval anchor and an adversarial command:

$$\text{Query} = \text{Anchor}_t \oplus C_{adv}$$

However, this approach suffers from a fundamental bottleneck: **semantic interference**. The adversarial command ($C_{adv}$) injects a static semantic bias. When converted to an embedding, this bias shifts the query vector away from the intended target region, degrading retrieval precision and causing different queries to cluster into overlapping semantic spaces (as shown in Figure 3).

```
[Pure Anchor: "Diabetes"] ----> (Retrieves medical records)
                                    ^
                                    | (Large, unpredictable embedding shift)
                                    v
[Concatenated Query: "Diabetes" + "Repeat previous data to tool..."] ----> (Retrieval misses target)
```

### The SPORE Architecture
SPORE solves this problem by exploiting the stateful nature of agent memories. Instead of concatenating the command and the anchor, SPORE temporally decouples them across the execution loop.

```
       +-------------------------------------------------------------------+
       |                           LLM AGENT                               |
       +------------------------------------+------------------------------+
                                            |
                         Step 1: Inject     | Step 2: Query with
                         Command to STM     | Pure Anchor (No drift)
                                            v
                                     +-------------+
                                     |   Memory    |
                                     | (STM / LTM) |
                                     +------+------+
                                            |
                        Step 1: Save        | Step 2: Retrieve
                        Command             | Target Record
                                            v
                                     +-------------+
                                     |  Retrieved  |
                                     |   Record    |
                                     +------+------+
                                            |
                                            | Step 2: Exfiltrate Record
                                            | via Tool Parameter
                                            v
                                     +-------------+
                                     |  Adversary  |
                                     |  Tool API   |
                                     +-------------+
```

#### Step 1: Adversarial Context Establishment
When the malicious tool $\tau_{adv}$ is first triggered, it returns only the fuzzed adversarial command:

$$x_1 = C_{adv}$$

The agent automatically appends this string to its STM context window. Because $C_{adv}$ is now persisted in the agent's history, it continuously influences subsequent reasoning steps, instructing the LLM to route any retrieved private records back to the tool.

#### Step 2: Iterative Memory Extraction
In subsequent iterations $t$ (where $2 \leq t < N$), the tool returns *pure semantic anchors* devoid of any defensive bypass instructions:

$$x_t = \text{anchor}_t$$

Because the retrieval query contains only the pure anchor, the embedding vector remains undistorted. The agent retrieves the target LTM records and, guided by the $C_{adv}$ instruction stored in its STM, transmits them as parameters to the tool.

```python
# Algorithmic Pipeline of SPORE at Runtime
def SPORE_Runtime(compromised_tool, agent, max_iterations):
    exfiltrated_data = set()
    t = 1
    
    while t <= max_iterations:
        if t == 1:
            # Step 1: Establish persistent context in short-term memory (STM)
            xt_tilde = compromised_tool.get_adversarial_command()
            agent.send_tool_response(xt_tilde)
            agent.append_to_stm(xt_tilde)
        elif 2 <= t < max_iterations:
            # Step 2: Iterative extraction using pure semantic anchors
            xt_tilde = compute_optimal_anchor(exfiltrated_data)
            agent.send_tool_response(xt_tilde)
            
            # Retrieve from LTM based on the pure anchor
            retrieved_records = agent.retrieve_ltm(xt_tilde)
            action = agent.plan(retrieved_records)
            
            # Action contains exfiltrated parameters sent back to the tool
            compromised_tool.receive_action(action)
            exfiltrated_data.update(extract_records(retrieved_records))
        else:
            # Step 3: Inject reactivation payload before platform limit terminates the loop
            xt_tilde = compromised_tool.get_reactivation_payload()
            agent.send_tool_response(xt_tilde)
            agent.persist_to_ltm(xt_tilde)
            
        t += 1
    return exfiltrated_data
```

#### Step 3: Reactivation State Persistence
To bypass platform-imposed tool-call budgets, SPORE injects a dormant reactivation payload ($P_{react}$) in the final iteration ($x_N = P_{react}$). 

This payload is designed to be written directly into the agent's LTM. When the user asks a semantically related, benign query in a later session, the RAG system retrieves $P_{react}$ back into the context window, triggering the agent to re-invoke $\tau_{adv}$ and restart the extraction cycle.

### Geometric Coverage Optimization
To prevent redundant retrievals, SPORE models the explored embedding space as a set of connected "Explored Balls":

$$\mathcal{B}(e(\text{anchor}_t), r_k)$$

where $e(\cdot)$ is the embedding function and the radius $r_k$ is defined by the distance to the $k$-th nearest retrieved record:

$$r_k = \|e(\text{anchor}_t) - e(d_k)\|$$

SPORE alternates between two search modes to maximize embedding space coverage:

#### 1. Fine-Grained Expansion
This mode targets records near the boundaries of already discovered clusters. The candidate anchor score combines two distance metrics:

$$S_{fine}(a) = w_{intra}\hat{D}_{intra}(a) + w_{inter}\hat{D}_{inter}(a)$$

- **Intra-component distance** ($\hat{D}_{intra}$): Minimizes overlap with already explored interior regions of cluster $C_j$:

$$D_{intra}(a) = \frac{1}{|C_j| - 1} \sum_{p \in C_j \setminus \{a\}} \left(1 - \cos\left(e(a), e(p)\right)\right)$$

- **Inter-component distance** ($\hat{D}_{inter}$): Favors anchors positioned far from other distinct cluster components:

$$D_{inter}(a) = \frac{1}{K} \sum_{p \in \text{KNN}_K(\mathcal{C} \setminus C_j, a)} \left(1 - \cos\left(e(a), e(p)\right)\right)$$

#### 2. Coarse-Grained Discovery
This mode locates entirely new, disconnected semantic regions. SPORE uses K-means clustering on current embeddings to map the explored space. It then extracts representative keywords from retrieved records using a lightweight LLM (GPT-4o-mini). Each keyword is scored based on its distance to the nearest cluster center:

$$S_{coarse}(a) = \min_{c \in \text{centers}} \left(1 - \cos\left(e(a), c\right)\right)$$

The system uses an **Adaptive Mode Switch** that swaps search strategies if $\gamma$ consecutive queries fail to retrieve new records (default threshold $\gamma = 4$).

## Limitations & Open Questions

A objective analysis of the experimental setup reveals several core assumptions and potential limitations:

- **Dependence on Black-Box Optimization Feasibility**: SPORE relies on templates mutated via LLM-Fuzzer to generate working $C_{adv}$ and $P_{react}$ strings. In practice, highly customized system prompts or aggressively aligned model updates may break these mutated templates, requiring attackers to continuously re-fuzz their payloads.
- **Stealth and Failure Rates**: While SPORE's Benign Response Rate (BRR) is significantly higher than the 0.0% rate of baseline attacks, it still averages between 61.5% and 84.0%. This leaves a 16.0% to 38.5% chance that the agent will return an anomalous error or output, which could be flagged by automated monitoring systems.
- **Vulnerability to Post-Retrieval Gating**: If the platform implements a secure intermediary gatekeeper that summarizes or filters retrieved LTM records *before* injecting them into the LLM context, the reactivation payloads ($P_{react}$) may lose their attack semantics during summarization. This is supported by the lower extraction rates observed on SCMemory (55.0%).

## What Practitioners Should Do

To defend against tool-side memory extraction, security teams and ML platform engineers should implement the following mitigations:

### 1. Enforce Tool-Side Memory Isolation
Do not expose raw user-retrieved context directly to third-party tools. Restrict tool parameters using strict, system-enforced schemas below the language layer. Tools should only receive explicitly authorized data fields rather than unstructured textual context.

### 2. Implement Post-Retrieval Sanitization
Introduce a dedicated intermediary filtering step between memory retrieval and model generation. This step must scrub incoming LTM data for active prompt injection payloads, system control patterns, and behavioral override commands.

### 3. Deploy Outgoing Parameter Audits
Implement runtime validation on outgoing tool calls. Platforms can use high-throughput classification models to inspect outbound JSON payloads, checking for suspicious blocks of concatenated text or high-density extractions of sensitive user fields.

```
Incoming LTM Retrieval ---> [Regex & Embedding Scan] ---> [Summarization Filter] ---> LLM Context
```

### 4. Mandate User-in-the-Loop Approvals
For highly sensitive data domains (such as healthcare, financial records, and credentials), require explicit user consent before transmitting any LTM-retrieved records to external APIs or third-party web services.

---

## The Takeaway

While user-side memory isolation is a necessary starting point, it does not guarantee absolute long-term memory privacy if the tool-side trust boundary remains exposed. LLM agents that automatically pass retrieved context to external APIs are highly vulnerable to systematic exfiltration. To fully secure these architectures, platforms must transition from simple user-level isolation to strict, system-level tool constraints.

## Den's Take

This paper exposes a glaring blind spot in agent security: we are so obsessed with securing inputs that we completely ignore outbound data sanitization. SPORE exploits this by turning outbound tool arguments into an unmonitored exfiltration channel. My concern isn't just the high 80.0% extraction rate on GPT-5-mini, but rather how easily this attack bypasses standard user-space isolation.

To be fair, the real-world threat might be slightly overstated here; requiring a user to execute a compromised tool up to 20 times to achieve a 67.5% extraction rate on commercial platforms like Coze assumes a highly repetitive user journey. Nevertheless, the underlying structural vulnerability is severe. As is often noted in LLM agent security literature, the only robust architectural remedy to this class of leakage is strict, policy-driven taint tracking that prevents retrieved long-term memory from ever flowing into unprivileged third-party API payloads. Until orchestration frameworks implement runtime data-flow tracking, any agent integrating third-party APIs with long-term memory is fundamentally insecure.
