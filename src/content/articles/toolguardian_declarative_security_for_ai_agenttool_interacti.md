# ToolGuardian: Secure AI Agent-Tool Interactions via Declarative ASP Policies

As Large Language Model (LLM) agents transition from sandboxed text generation to executing actions via Model Context Protocol (MCP) servers, the security perimeter shifts dramatically. Orchestration environments delegate system access to integrations that can hide malicious behavior behind entirely benign-looking interfaces. ToolGuardian addresses this vector by separating tool analysis from policy enforcement, introducing a structured, logic-based mediation layer to block rogue tool actions.

---

## Threat Model

The security boundaries of tool-augmented AI agents are vulnerable to implementation-level attacks. ToolGuardian assumes a threat model where the host operating system is secure, but the external tools are untrusted.

| Vector | Description |
|---|---|
| **Attacker** | A malicious developer or third-party package maintainer who embeds hidden capabilities (e.g., exfiltration, local state mutation) inside an otherwise functional MCP tool. |
| **Victim** | AI agent workflows executing delegated tool calls. |
| **Goal** | Exfiltrate secrets, manipulate local files/databases, bypass host boundaries, or perform multi-tool composition attacks (e.g., executing a sensitive read using Tool A and exfiltrating via Tool B). |
| **Capabilities** | The adversary controls the implementation of one or more tools, allowing them to embed hidden malicious behavior. |

## Background and Problem Setup

Existing defenses fall into two flawed paradigms: scanner-style static analysis that lacks task context, and runtime LLM-based self-policing that lacks determinism and is vulnerable to prompt injection. 

Related work, such as MalTool (Hu et al. [2]), has demonstrated that malicious tools can preserve benign interfaces while embedding code-level behaviors that violate security properties. Static scanners (e.g., Cisco's MCP-Scanner [9] or MCPScan.ai [10]) often fail to differentiate between a tool's legitimate administrative capabilities and an active exploit attempt during runtime.

| Defense Paradigm | Characterization Evidence | Policy Enforcement Style | Composition Aware? | Reasoning Determinism |
|---|---|---|---|---|
| **Static Metadata Scanners** (e.g., [9], [10]) | Shallow descriptions, manifests | Hardcoded signatures / rules | No | High |
| **Prompt-Based LLM Guards** (e.g., [12], [13]) | None (evaluates raw prompts) | Heuristic system prompts | No | Low (Stochastic) |
| **ToolGuardian** (This work) | Multi-layered ($L_0$ to $L_3$) | Declarative Logic Programming (ASP) | Yes (explicit compositional rules) | High (Formal Logic) |

## Methodology

ToolGuardian uses a dual-stage pipeline: **Layered Tool Characterization** and **Declarative Policy Evaluation**.

```
[External Tool] ──> [Dynamic/Static Characterization (L0-L3)] ──> [Normalized Facts] ──> [ASP Policy Solver (Clingo)] ──> [Decision: Allow/Block/Restrict]
```

### 1. Progressive Characterization (Layers $L_0$ to $L_3$)
To collect evidence without over-relying on single detection techniques, the system defines four cumulative characterization tiers:
- **$L_0$ (Description):** High-level natural language capabilities mined from manifest files and readmes.
- **$L_1$ (Syscall Traces):** Coarse operating system activities (file reads, socket creation) logged during tool execution.
- **$L_2$ (Mock Execution):** Dynamic behaviors observed during sandboxed execution with simulated inputs (e.g., HTTP POST destinations, state mutations).
- **$L_3$ (Static Source AST):** Source-code parsing using Abstract Syntax Trees to locate unexecuted conditional logic or dormant API endpoints.

These inputs are normalized into declarative facts:
```prolog
capability(tool_016, database_access).
accesses_data(tool_016, database_records).
observed_effect(tool_003, http_request).
```

### 2. ASP-Based Policy Reasoning
These facts are fed into Clingo, an Answer Set Programming (ASP) solver. Instead of using imperative logic (like Python if-statements) or stochastic logic (LLMs), ASP maps policies as formal constraints. For example, a policy blocking any tool combining sensitive data access with network requests is represented in ASP as:

```prolog
% Tool-level sensitive-data access.
sensitive_data_tool(T) :-
    accesses_data(T, database_records).

% Tool-level external communication.
external_network_tool(T) :-
    capability(T, network_access),
    observed_effect(T, http_request).

% Tool-level denial.
deny_tool(T, sensitive_data_network_risk) :-
    sensitive_data_tool(T),
    external_network_tool(T).

% Enforce vetting decisions
vetting_decision(T, admit) :-
    tool(T),
    not deny_tool(T, _).
```

This declarative model enables ToolGuardian to track multi-tool workflows at runtime. If Tool A (authorized to read DB records) executes, and subsequently Tool B (authorized to call APIs) is invoked, the compositional rules detect the causal information flow and block Tool B, even though both tools are individually benign.

## Limitations and Open Questions

Despite the strong performance metrics, several design tradeoffs exist within this architecture.

- **The Static Analysis Deficit ($P_3$ Overblocking):** As shown in Table III, advancing from $P_2$ to $P_3$ decreased vetting accuracy for both ASP and LLM realizations (dropping from 88% to 81%). The introduction of static AST parsing ($L_3$) exposed latent capabilities within benign tools (such as local subprocess execution combined with screen capture in administrative shell tools). This led to two false positives, classifying legitimate management tools as malicious.
- **Dynamic Analysis Evasion:** Characterization tiers $P_1$ and $P_2$ rely heavily on active runtime tracing. Behaviors that remain unobservable under the available characterization or runtime monitoring infrastructure may evade detection.
- **Scale and Co-Design Bias:** The evaluation was conducted on a controlled benchmark of 16 tools and 20 scenarios. Real-world applications feature a significantly larger and more diverse tool ecosystem, which may introduce additional rule complexity and edge cases.

## What Practitioners Should Do

If you are deploying LLM agents with tool integration capabilities, consider implementing these defense steps:

1. **Enforce Sandboxed Tool Runtimes:** Never run MCP servers or local tools directly on host development environments. Run them within secure sandboxes or isolated execution environments to limit the impact of actions like unauthorized file read/write operations.
2. **Collect Multi-Tier Evidence:** Set up an automated testing pipeline that executes newly imported tools inside a tracer-enabled sandbox to monitor system calls and verify their dynamic behavior against their manifest descriptions before deployment.
3. **Deploy a Decoupled Policy Engine:** Do not rely on LLMs to self-police tool calls. Use a deterministic rule engine (such as Clingo for ASP) to evaluate structured tool traits against user session permissions.
4. **Implement Composition-Aware Runtime Policies:** Ensure your policy layer evaluates the interaction and sequence of tool calls. If an agent executes a tool that accesses sensitive local database records, the runtime policy should detect this context and block subsequent tool invocations that request external network communication.

## The Takeaway

Securing AI agents requires moving beyond basic system prompts and one-time static file scanners. ToolGuardian demonstrates that converting raw system behaviors into structured, logical facts is an effective way to verify tool functionality. Relying on declarative reasoning over these facts allows developers to block malicious actions at runtime without degrading the agent's core capabilities.

---

## Den's Take

Formalizing security policies via Answer Set Programming (ASP) is a theoretically elegant approach to the chaotic state-tracking problems in agentic workflows. However, ToolGuardian’s reliance on mapping dynamic tool behaviors into rigid, deterministic logic facts introduces a fragile dependency on the translation layer itself. 

If we examine the evaluation, the limitations become obvious. Testing on a tiny corpus of just 16 MCP-style tools is closer to a proof-of-concept than a robust validation. An 88% accuracy rate and a deny-class F1-score of 0.86 at tier $P_2$ on such a minuscule sample suggests the system will struggle with high false-positive rates when confronted with the messy, undocumented APIs typical of enterprise deployments. 

As shown in research on agent security, intermediate security layers in tool-augmented environments can be highly prone to failures that degrade agent utility. ToolGuardian attempts to bypass LLM non-determinism with formal logic, but it merely shifts the vulnerability. Sophisticated attackers will exploit the semantic gap between how a tool is statically characterized into ASP facts and how its dynamic payload actually executes at runtime. Enterprise security teams should remain skeptical of ASP's real-world scalability until we see evaluation sets scale by orders of magnitude.
