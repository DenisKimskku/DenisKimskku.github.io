# HoF-Bench: Evaluating LLM Vulnerability Scanning Capabilities on Real AI-Discovered CVEs

Modern development environments are increasingly integrating agentic vulnerability scanners to secure high-profile open-source software, yet the actual capabilities of these models remain poorly understood. While tools targeting production codebases have claimed hundreds of zero-day discoveries, benchmarks have historically focused on trivial code snippets rather than real, multi-file codebases like OpenSSL, curl, or GnuTLS. This study introduces HoF-Bench, a standardized benchmark designed to systematically evaluate how reliably non-frontier Large Language Models (LLMs) can rediscover real-world, AI-found Common Vulnerabilities and Exposures (CVEs) within pinned software repositories.

| | |
|---|---|
| **Attacker** | An automated scanner attempting to identify vulnerabilities using black-box or API-based LLMs without access to ground-truth CVE identifiers, descriptions, or patch files. |
| **Victim** | Mature, open-source repositories pinned at vulnerable commits (e.g., OpenSSL, curl, GnuTLS, Apache httpd, pearweb, FOGProject, OpenEMR, WeKan). |
| **Goal** | Achieve strict rediscovery of a specified CVE, matching the ground-truth vulnerable code path, root cause, attacker-controlled entry point, and security impact. |
| **Budget** | Limited to small, low-cost "flash-tier" or open-weight Mixture of Experts (MoE) models, with pricing ranging from \$0.03 to \$1.50 per million input tokens. |

## Background / Problem Setup

Vulnerability detection has transitioned from simple pattern-matching Static Application Security Testing (SAST) tools to generative LLM-based systems. However, measuring whether these systems can reliably find real vulnerabilities is difficult. Most existing benchmarks fall short because they use synthetic code snippets, isolate single functions, or evaluate only a single programming language. 

To resolve this, HoF-Bench introduces a source-conditioned evaluation protocol. Instead of demanding repository-wide autonomous localization, the benchmark targets specific files containing a median of 911 source lines, evaluating whether the model can reason through the code to locate and describe the exact vulnerability.

As shown in the table below, HoF-Bench addresses critical gaps left by prior vulnerability benchmarks:

| Benchmark | Level of Evaluation | Multi-Language Support | Code Realism | Evaluation Metric |
|---|---|---|---|---|
| **Devign** (Zhou et al.) [22] | Function-level | No (C only) | Synthetic/Isolated | Binary Classification |
| **Snyk VulnBench JS 1.0** [17] | Repository-level | No (JavaScript only) | Small fixtures | Repeatability |
| **RealVuln** (Pellew & Raza) [12] | Repository-level | No (Python only) | Intentionally vulnerable repositories | Finding match |
| **HoF-Bench** (Simecek et al.) | Source-conditioned | Yes (C, PHP, JavaScript) | Pinned production repos | Strict multi-dimensional identity match |

## Methodology

The reference scanner evaluated in this study utilizes a pipeline inspired by the open-source `nano-analyzer` project [7], as illustrated in Figure 2:

```
[Scanner Input] ---> [Optional Context] ---> [Detector Model] ---> [Skeptical Triage] ---> [Blinded Evaluator]
```

1. **Scanner Input**: The scanner is provided with a repository checked out at a pinned, vulnerable commit and 1–7 designated target files.
2. **Optional Context**: When enabled, a model generates a concise security briefing detailing entry points, trust boundaries, and data flow. The model may additionally issue up to three literal repository searches (e.g., finding callers of a specific function).
3. **Detector Model**: A non-frontier model parses the target files (and optional context) to generate structured candidate findings, capped at five raw findings per pass. Ten detector models were evaluated, split evenly between open-weight and proprietary options:
   - *Open-weight*: GPT-OSS 20B, GPT-OSS 120B, DeepSeek V4 Flash, Qwen 3.6 35B A3B, Mistral Small 4.
   - *Proprietary*: GPT-5.4 nano, Gemini 2.5 Flash, GPT-5.4 mini, GPT-5.6 luna, Gemini 3.5 Flash.
4. **Skeptical Triage**: Findings undergo three sequential rounds of triage where reviewer models vote to validate or reject them, followed by an arbiter model that delivers a final valid-or-invalid decision.
5. **Blinded Evaluator**: A frontier model (GPT-5.6 terra), entirely blinded to the detector model's identity and pass number, evaluates the surviving findings against the ground truth. To achieve a **strict match**, the finding must successfully identify:
   - The same vulnerable code path or component.
   - The correct root cause.
   - The attacker-controlled condition or trust boundary.
   - The actual security impact.

The evaluator assigns one of four strict classifications: `match`, `partial`, `no match`, or `insufficient evidence`.

## Limitations & Open Questions

A close examination of the study's results reveals several areas where practitioners should remain skeptical:

- **Localization Oracle**: The benchmark provides target files directly (a median of 911 lines). This means the benchmark does not test repository-wide discovery capabilities; real-world scanners must first solve the difficult task of finding *where* to look.
- **The Context Overhead Paradox**: As seen in Figure 6, generating code context often costs significantly more than the negligible recall it adds. Across all 950 model-CVE pairs, context only improved strict rediscovery by 21 instances (54.1% vs 51.9% without context). However, context bloated the deduplicated finding count from 1,664 to 2,088, increasing the human review burden to 4.1 findings per rediscovered CVE (compared to 3.4 findings without context).
- **Stylistic Evaluator Bias**: The blinded judge (GPT-5.6 terra) is from the same model family as several detector backbones (GPT-5.4, GPT-5.6). Although the evaluator was blinded, stylistic affinity and formatting matching between models of the same family could skew the strict match grading.
- **Data Contamination**: Because the evaluation target is a set of historical, publicly disclosed CVEs, we cannot rule out the possibility that some models memorized parts of the vulnerable code or disclosures during pre-training.

## What Practitioners Should Do

For security teams and developers building automated LLM-based scanners, these results suggest several concrete changes:

1. **Implement Multi-Pass Scanning**: Never rely on a single LLM scan. Moving from 1 pass to 4 passes consistently added between 12 and 20 rediscovered CVEs per model (as shown in Figure 3).
2. **Deploy Diverse Model Portfolios**: Rather than repeatedly calling a single expensive frontier model, combine cheaper, distinct architectures. Splitting 12 passes across three inexpensive models (e.g., DeepSeek V4 Flash, Qwen 3.6, and Gemini 3.5 Flash) yielded 70 rediscovered CVEs for only \$66—outperforming four passes of the premium GPT-5.6 luna, which cost \$128 (Section 5.1).
3. **Skip Complex Context Generation for Web Languages**: When scanning JavaScript or PHP codebases, skip the expensive contextual briefing and multi-round repository searches. These languages exhibit high pass@4 rediscovery rates (81% and 63% median respectively), meaning the added context serves primarily to generate noisy, duplicate candidates.
4. **Enforce Semantic Deduplication**: Group incoming scanner outputs using deterministic similarity rules and an LLM-based consolidator before pushing them to human reviewers. This mitigates the 4.1 findings-to-CVE ratio and prevents human analyst fatigue.

## The Takeaway

Vulnerability scanning with LLMs is a systems engineering challenge, not just a raw model capability problem. Relying on small, inexpensive models within a robust multi-pass and multi-agent scaffold can match or exceed the performance of a single costly frontier model run. However, the stark performance gap in stateful C codebases underscores that complex logic and memory-safety bugs still require deep, cross-file reasoning that current small models cannot reliably navigate.

## Den's Take

While HoF-Bench provides a much-needed injection of realism by ditching toy synthetic snippets, the authors' "source-conditioned" methodology actually introduces a massive bias that inflates the perceived readiness of non-frontier models. Handing a model a pre-isolated file with a median of 911 lines completely bypasses the hardest phase of vulnerability discovery: repository-scale localization. 

If the best-performing model can only manage a 62% rediscovery rate on C code *after* being pointed directly to the culprit file, its real-world utility in a messy multi-file codebase is virtually non-existent. This massive performance gap between JavaScript (100%) and C (62%) highlights that these models still rely on syntactic pattern matching rather than robust semantic reasoning about memory management.

As I've noted in prior reviews, LLMs depend heavily on tightly bounded contexts to reason about software defects, and repository-wide comprehension remains an unsolved bottleneck. Deploying these "flash-tier" models costing \$0.03 to \$1.50 per million tokens into live pipelines will yield a deluge of false negatives in low-level code, meaning SecOps teams should treat these automated scans as cheap, noisy hints rather than a replacement for manual security audits.
