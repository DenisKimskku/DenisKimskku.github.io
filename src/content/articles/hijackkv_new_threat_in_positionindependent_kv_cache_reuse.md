## TLDR
- **What**: HijackKV is an attack that exploits position-independent Key-Value (KV) cache reuse to condition shared cache chunks with adversarial prefixes, silently steering model outputs on future user queries without any adversarial text in the victim's input.
- **Who's at risk**: Multi-tenant Large Language Model (LLM) serving frameworks (such as vLLM [48] or SGLang [64]) running chunk-level position-independent cache sharing engines (such as LMCache [28], CacheBlend [62], EPIC [14], or MEPIC [49]).
- **Key number**: HijackKV achieves an average Targeted Attack Success Rate (T-ASR) of 89% on Llama-3.1-8B across the evaluated datasets and recomputation methods, and maintains a 47% success rate when up to 2,048 tokens of unrelated filler conversational context are inserted before the victim's query.

---

Multi-tenant Large Language Model (LLM) serving infrastructures rely on aggressive caching strategies to reduce the Time-to-First-Token (TTFT) latency under heavy workloads. Production optimizations like LMCache [28] and CacheBlend [62] introduce position-independent Key-Value (KV) cache reuse, which allows identical text segments—such as shared organizational knowledge bases, Frequently Asked Questions (FAQs), or system prompts—to reuse cached states regardless of where they appear in a sequence. However, a recent paper reveals that decoupling KV states from their preceding causal context creates a severe security vulnerability: an attacker can silently hijack model behavior for downstream users without inserting any malicious tokens into the victim's input prompt.

## Background & Problem Setup

To eliminate redundant computations during LLM generation, inference engines store computed Key (K) and Value (V) projection matrices in a GPU-based KV cache. Traditional prefix-based caching is strict: it requires exact match of both tokens and their relative position indexes. 

To improve cache hit rates, recent system optimizations introduce position-independent cache reuse. This mechanism splits long documents into smaller chunks (e.g., 32 tokens) and caches them individually. If a chunk matches a segment of a user's prompt, the precomputed KV cache is retrieved and reused, even if the preceding context differs.

However, because self-attention is fundamentally context-dependent, a chunk's KV representations change depending on the preceding tokens. Modern engines use "selective recomputation" (e.g., recomputing 10-20% of high-influence tokens) to correct this misalignment and maintain accuracy. The authors of the paper show that this partial recomputation is insufficient to prevent deliberate security exploits.

## Methodology

HIJACKKV operates in two distinct phases: prefix optimization on a surrogate model, followed by injection into the target system's shared cache. 

```
Phase 1: Attacker (Surrogate Model Optimization)
[Adversarial Prefix p] + [Benign Chunk X_tilde] -> LLM -> Extract KV Cache of X_tilde (T_p)
Optimize p using GCG to minimize Cross-Entropy Loss on malicious target answer r_tilde.

Phase 2: Target LLM Infrastructure (Cache Poisoning)
Attacker submits: [Optimized Prefix p] + [Benign Chunk X_tilde]
Inference Engine computes KV cache and stores the poisoned KV cache of X_tilde into Shared Pool.

Phase 3: Victim Query (Execution)
Victim submits: [Benign Chunk X_tilde] + [Query q]
Inference Engine reuses poisoned KV cache of X_tilde.
LLM outputs: [Malicious Target Answer r_tilde] (No adversarial text in victim input).
```

### The Optimization Objective

The attacker optimizes an adversarial prefix $p$ to find tokens that condition the KV cache of a benign segment $\tilde{X}$, denoted as $\mathcal{T}_{\tilde{X}}^p$, such that when a victim combines $\tilde{X}$ with their query $q$, the model generates the target response $\tilde{r}$:

$$p^* = \arg\min_{p} \mathcal{L}_{CE} \left( \text{LLM}(X \oplus q \mid \mathcal{T}_{\tilde{X}}^p), \tilde{r} \right)$$

where $\mathcal{L}_{CE}$ is the cross-entropy loss.

The optimization process is executed locally via the Greedy Coordinate Gradient (GCG) [65] algorithm. Below is the pythonic representation of the loss evaluation loop simulating position-independent cache reuse:

```python
def compute_loss(prefix_tokens, target_chunk_tokens, query_tokens, target_response_tokens, model, embedding_matrix):
    # Step 1: Compute continuous embeddings of the adversarial prefix
    prefix_embeddings = embedding_matrix(prefix_tokens)
    chunk_embeddings = embedding_matrix(target_chunk_tokens)
    
    # Step 2: Extract the conditioned KV cache corresponding to target_chunk
    full_embeddings = concat([prefix_embeddings, chunk_embeddings], dim=0)
    full_kv = model.compute_kv(full_embeddings)
    
    # Slice to isolate only the target chunk's KV cache (discarding prefix states)
    prefix_length = len(prefix_tokens)
    poisoned_chunk_kv = full_kv[:, :, prefix_length:, :] 
    
    # Step 3: Simulate victim inference reusing the poisoned chunk cache
    query_embeddings = embedding_matrix(query_tokens)
    output_logits = model.inference_with_cache(query_embeddings, cached_kv=poisoned_chunk_kv)
    
    # Step 4: Compute loss against the designated target response
    loss = cross_entropy_loss(output_logits, target_response_tokens)
    return loss
```

## Key Results

The authors evaluated HIJACKKV across multiple question-answering datasets—including SQuAD (v1.1/v2.0) [39, 40], HotpotQA [61], MedQA [18], and PubMedQA [19]—using Llama-3.1-8B, Mistral-8B (evaluated as Ministral-8B in the paper's implementation), and Qwen3-8B. The evaluations were performed under a default cache ratio of $\delta = 0.3$ (meaning 30% of the context is served from the cache) and a recomputation ratio of $\rho = 0.1$ (10% of the cached tokens are recomputed).

The following table presents the Targeted Attack Success Rate (T-ASR) on the HotpotQA and SQuAD datasets across three representative models under different recomputation methods:

These results demonstrate that existing recomputation methods like EPIC and CacheBlend fail to secure systems against HIJACKKV. Even under EPIC's defensive recomputation, the attack maintains a T-ASR of at least 75% on SQuAD and 85% on HotpotQA.

## Limitations & Open Questions

1. **Cache Eviction and Replacement Policies**: The attack relies on the poisoned cache remaining inside the shared pool. In real-world environments, cache replacement policies (such as Least Recently Used [LRU] or First-In, First-Out [FIFO]) will eventually evict the poisoned chunks. If a target segment is highly popular, it may be continuously refreshed, but it is also harder for an attacker to overwrite an existing entry without causing collisions.
2. **Probing Cache Occupancy**: To execute the attack reliably, an attacker must know whether the target segment is currently cached. While the paper outlines a side-channel timing analysis that achieves 81.4% accuracy with a single query, this probing is not fully passive and might trigger rate limits or anomaly detection systems.
3. **Adaptive Attack Cost**: Mitigating the attack by increasing the recomputation ratio (e.g., to $\rho = 0.5$) decreases the success rate, but also introduces a severe latency penalty. The optimization process can also adapt to this defense: if the attacker includes recomputation during the local GCG loop (as shown in Section 7.6), the attack remains robust even against highly defensive recomputation settings.

## What Practitioners Should Do

Organizations deploying shared cache engines must review their configurations immediately. To protect systems against HIJACKKV, take the following steps:

- **Enforce Boundary Constraints in Multi-Tenant Settings**: If your system serves multiple untrusted tenants, disable position-independent chunk-level sharing across security boundaries. Use strict prefix-based sharing (like Radix Attention in SGLang [64]) where the cache is retrieved only if the entire preceding prompt sequence matches.
- **Implement a Deviation-Based Rejection Policy**: When retrieving a position-independent cache chunk, perform a lightweight recomputation of a random subset of key tokens. Deny cache reuse if the deviation of the recomputed KV states compared to the cached states exceeds a predefined safety threshold (e.g., $\geq 20\%$).
- **Isolate Cache Pools by Privilege Level**: Segment the global cache pool. Avoid sharing cached states from administrator documents, system configurations, or highly sensitive internal corpora with the cache pools accessible to unprivileged external users.
- **Configure Hybrid Recomputation Heuristics**: If position-independent caching is required for performance, implement the `Attn Score` recomputation defense shown in Table 11. Increasing the recomputation ratio to $\rho = 0.6$ reduces the attack's T-ASR to 22.5%, though this will increase the normalized recomputation cost by approximately 2.97x.

## The Takeaway

HIJACKKV exposes a fundamental security trade-off in high-throughput LLM architectures, demonstrating that position-independent cache optimization breaks the causal alignment of Transformer-based models. By decoupling cached keys and values from their preceding historical tokens, these performance-focused systems introduce a stealthy, input-free attack vector. Security teams must treat the KV cache as a privilege boundary, recognizing that raw computational efficiency cannot come at the expense of context integrity.

## Den's Take

We are seeing a classic security pattern play out: performance optimizations in AI systems are constantly introduced without considering state isolation. Position-independent caching mechanisms like LMCache and CacheBlend are brilliant for driving down latency, but decoupling a token’s Key-Value representation from its causal history breaks the fundamental security boundaries of multi-tenant systems.

However, the practical threat of HijackKV is narrower than this paper suggests. The authors rely on Greedy Coordinate Gradient (GCG) optimization to generate their adversarial prefixes. Anyone who has run GCG in production knows it is incredibly fragile. While the paper demonstrates an impressive 89% T-ASR on Llama-3.1-8B, these optimized perturbations are highly sensitive to the exact precision of the KV cache. Production deployments of SGLang and vLLM almost universally utilize low-bit quantization to maximize throughput. This quantization noise will likely destroy the precise mathematical alignments required by the GCG prefix, rendering the attack far less reliable in the wild.

As I've noted in previous reviews of RAG security, attackers will always target the weakest link in the context retrieval pipeline to bypass explicit prompt filters. HijackKV takes this concept down to the shared caching infrastructure. To defend against this, practitioners must act now to enforce strict tenant isolation within shared cache pools, even if it means sacrificing some of the deduplication savings that position-independent engines promise.
